# Subsequent-event register: keep the condition, event and review dates separate

**Reader edition 2026-10-05.1** · Wording changes are limited to labels and notices. Earlier check statements refer to the original article revision. No new professional review or source verification is claimed.

**Educational draft · v1.1.0 · 2026-10-04 · Editorial checks only; no human professional review.**

## Scope cover

Record the actual entity/framework, financial-statement date, proposed issuance or availability date, audit-report date if relevant, evaluation endpoint and the authority supporting that endpoint. Leave a missing date unresolved. This is an original working format, not a complete mandatory accounting or audit checklist.

Primary ASC text was not accessed to prepare the template. ASC 855 is a research starting point, not an inspected rule governing this packet. Reissuance and later-discovered facts require their own scope analysis. [fasb-asc]

## Event-level fields

| Field | Record or explicitly mark unknown |
|---|---|
| Event identity and description | Stable ID; short neutral description |
| Underlying condition | Claimed onset; evidence supporting or contradicting it |
| Event and discovery dates | Separate dates with evidence; no silent backdating |
| Record identity | Actual document/version/hash if retained; exact locator |
| Financial effect | Amount/unit, source, estimate or assumption status |
| Accounting question | Recognition and disclosure considered separately |
| Audit/report question | Applicable engagement and separate reporting dates |
| Proposed next work | Actual assigned owner if any; missing evidence |
| Decision record | Exact revision, actual reviewer, scope/date and unresolved items |

These are blank workpaper fields. They do not represent performed procedures or real approvals.

## Original filled example

In a fictional register, reporting date is December 31; a customer sends a January 12 letter; the preparer receives it January 15; the letter alleges financial difficulties beginning November 20. Record all four dates. The condition-onset field is “November 20 asserted by customer; corroboration pending,” not “November 20 confirmed.”

The receipt date does not prove when the underlying condition began. The letter also does not decide an adjustment, required disclosure or audit-report change. Add the actual applicable criterion and supporting facts before resolving those separate questions.

## Update procedure

Preserve the earlier record when new information arrives. Add what changed, who supplied it, when it became available and which prior claim it affects. Reassess the relevant conclusion without making the new record appear to have existed earlier.

If a reviewer considered only selected events or a period ending before the required endpoint, record that scope limit. “No further events identified in the work performed” is narrower than an assertion that no events exist. Any completeness conclusion requires evidence of the actual process and its scope.

## Release checklist

Confirm the intended reporting period and verified evaluation endpoint; attach the event chronology, gaps, source access status and actual review record. Preserve the historical status of old review declarations, but do not display an old revision's approval as approval of changed facts or wording.

Keep sensitive client material out of public contributions. The template can remain useful with open questions; it cannot certify a completed subsequent-event review, supply legal advice or authorize a filing.
