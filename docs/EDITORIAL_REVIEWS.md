# Technical review records (#23)

Rights, technical correctness and historical applicability are separate decisions. A content import or model pass cannot supply an independent human review. Original commentary remains commentary after technical approval.

An assigned technical reviewer opens **Content review**, inspects the source and listed reference limitations, and records a decision against the displayed revision. The source author cannot review their own submission. Independent rights approval comes first; approval also requires current permission to inspect the full source body. Real accounts continue to require server-verified email and MFA. Local demonstration identities are test fixtures only.

Each decision requires a scope, findings, a private supporting-record identifier (`ev_…`) and SHA-256, an explicit future expiry, checked reference IDs and an attestation that the review actually occurred. The identifier/hash binds the submitted assertion; it does not prove the supporting document exists, verify a license or establish reviewer competence. Keep the actual evidence in an approved private channel. Do not put confidential legal advice or restricted source text in public issues.

`POST /editorial/sources/{id}/review` accepts approved, changes_requested, rejected or revoked. Approved decisions must address every listed reference. The service checks policy version, actual body hash and a canonical revision containing title, publisher, URL, edition, framework, kind, reference IDs and retained citation/provenance fields. Referenced publication bodies are not automatically fetched or reviewed. Applicability dates have their own review and are excluded from the technical fingerprint.

Decisions append to `editorial_reviews`; there is no edit/delete API. Each new decision increments the source policy version and replaces the current-record pointer while preserving prior records. Source-row locks prevent a stale concurrent decision overwriting a newer decision. Corrections require another decision against the current revision. Revocation or expiry immediately denies uses that require technical approval. The runtime also checks the selected record's payload hash, source binding and revision. This is application-level immutable history, not a cryptographically signed or database-administrator-proof archive.

**Review history** calls `GET /editorial/sources/{id}/reviews`, returning the latest 100 records. It requires a technical-reviewer role and current full-display permission; the output-rights ledger also applies because findings may quote a source. Findings are stored in the private ledger instead of public source-policy metadata. Disabled sources are inaccessible through this view.

Migration `0010_editorial` adds the ledger. It does not backfill approval records from old flags: a legacy approved flag alone no longer permits Agent use or SEC applicability approval. Real reviewers must submit fresh revision-bound records. Public educational display remains a separate rights-controlled operation. Apply the normal Alembic migration before running the new API.

Remaining #23 work includes linked-publication dependency snapshots, applicability UI/SEC reconciliation, coverage reconciliation and independent human reviews. The synthetic tests and UI fixture do not advance real-content approval counts.

## Review packets and reference snapshots

**Download review packet** exports JSON for one displayed source revision. The API is `GET /editorial/sources/{id}/packet?expected_review_revision=HASH&expected_policy_version=N`. It requires the technical-reviewer role, current full-display permission **and** export permission. Source locking, lineage checks, output limits and notices still apply. The packet contains the actual draft/body hash, citation/provenance fields, gates, an explicit review checklist and a canonical SHA-256 of its `packet` object (UTF-8 JSON, sorted keys, no spacing, unescaped Unicode). The digest detects content changes; it is not a signature or professional attestation. Identical packets reuse the same output-ledger release fingerprint.

The export omits previous technical findings, supporting records and private SEC applicability notes. It does not fetch references, export linked full text or grant Agent admission. Share a packet only through the operator-approved private review channel; the application does not send it to a reviewer. Recheck live permissions/revisions before acting on any exported copy. A downloaded copy cannot be recalled automatically.

New original-library staging preserves sorted, complete reference-metadata snapshots and their digest. The technical revision binds both the IDs and the actual snapshot. Updating the live file pack does not silently change a staged version. Re-importing an existing item/version with changed reference metadata or no previously captured metadata fails: publish a new version and obtain the separate reviews. Do not retrofit missing snapshots into an existing approval. Legacy original-library sources without valid snapshots cannot receive/currently retain technical approval; their export explicitly labels references `not_captured` so the gap can be assessed. This change does not alter shipped article versions or fabricate historical snapshots.

Captured metadata is still reference-only. It does not establish rights or the revision of the linked publication itself. SEC/intake sources continue to bind their existing exact provenance; they are not falsely labeled as having original-library metadata snapshots. General linked-publication dependency graphs remain open; later sections describe implemented comparison and parser/applicability records. Browser download verification is tracked in reports/intake/REVIEW_PACKETS.md.

## Parser and citation decisions

Migration `0011_parser` adds `parser_reviews`. It creates no human approvals. Parsed text may still be staged as unapproved drafts, but intake-derived passages cannot enter Agent/model operations without a current parser decision, independent rights, technical review and applicable date checks. Parser review does not satisfy the other gates.

Assigned technical reviewers can open **Parser review** in the account header (`/parser-review`). The interface lists 30 extraction records per page, presents 25 passages per page with persistent explicit checks, and shows scope/findings/evidence/expiry fields and private history. Decisions default to Request changes. Approval requires every passage check and an actual-inspection attestation. Submitted records lock the form until reload. Artifact and JSON downloads recheck current permissions and revision. Underlying API endpoints:

- `GET /editorial/extractions/{id}/packet`: original bytes as base64, original MIME, actual raw/normalized hashes, parser version, exact passage locators/text, edition/publication metadata, notices, current review sequence and review checklist. The raw bytes are not executed. Inspect original artifacts with a suitable isolated viewer. Requires current store-raw/store-text/display/export operations; output budgets apply.
- `POST /editorial/extractions/{id}/review`: `ParserDecision` in the generated OpenAPI contract. Requires exact expected revision/sequence, scope/findings, private supporting-record reference/hash, expiry, checked zero-based passage indices and actual raw/citation inspection attestation. Approval covers every passage. The source author, acquisition operator and recorded parsing actor cannot act as the independent reviewer. Rights remain independently approved. The operation requires current storage/display rights and intact artifacts; if those are lost, disable the source while resolving the gate instead of claiming a new inspection.
- `GET /editorial/extractions/{id}/reviews`: latest 100 private decision records, sequence order, with payload hashes. Reviewer role, current storage/display permissions and normal output budgets apply.

Decisions append under a parent source lock with a unique extraction/sequence constraint. Concurrent stale submissions fail. The decision binds raw hash/size/receipt, normalized hash, parser version, passage count, manifest and parent policy/revision. It also records every passage hash and locator. Staged passages carry their exact extraction, parser, ordinal and normalized hash. Approval expiry, revocation, changed metadata, source text/citation or inconsistent records deny runtime use. Each new parser decision increments affected staged-source policy versions, invalidating saved evidence. Saved evidence access/export additionally checks current parser review, so expiry also withholds dependent output without requiring a background job.

The runtime checks database provenance and staged text; it does not reread the entire stored original on every query. Packets and new decisions verify actual stored bytes. Application-immutable records and hashes are not signatures or protection against a database/storage administrator. Private supporting records are referenced, not fetched or independently authenticated by this API.

Legacy staged intake passages lack the new ordinal/hash/parser binding and remain blocked; do not fabricate or silently backfill historical approval. Register/reparse a new immutable edition and obtain its reviews. The bundled selected SEC excerpt workflow is distinct from acquired intake extractions and is not falsely counted as parser-reviewed full publications. Coverage reconciliation and actual independent reviews remain open; later sections describe comparison and general applicability records.

The parser worklist (`GET /editorial/extractions`) is reviewer-only metadata, with bounded pagination and no artifact reads. It reports the last recorded decision, not a promise of current admission. Raw and extracted text remain gated by the existing packet endpoint. The UI renders passages/findings as literal text and downloads original bytes as application/octet-stream, never executable inline markup. Large-corpus usability, broader accessibility and actual browser download completion remain validation tasks; see reports/intake/PARSER_UI.md.

## Comparing staged revisions

From **Content review**, choose **Compare versions**, select a baseline and select **Show changes**. The current card is the comparison target. The reviewer chooses direction explicitly; the application does not guess which edition is authoritative or chronologically applicable.

`POST /editorial/compare` uses the `RevisionComparison` schema with both source IDs, expected review revisions and expected policy versions. Both sources are locked in ID order and must currently permit full display. Both sources' output notices and budgets apply. This is a display operation; no comparison export or grant transfer is provided.

Supported identity pairs are the same original content item, the same intake family/work/exact passage locator, or the same bundled SEC source/passage ID. Edition/snapshot differences are retained. Matching a URL alone is insufficient. Renumbered or restructured passages require separate reconciliation; this endpoint will not invent a relationship. It compares two existing staged versions and cannot reconstruct an overwritten historical body.

Results preserve exact changed lines (including newline differences), one-based starting line numbers, body/review hashes, metadata differences and source notices. Reference metadata changes are visible even if the article body is identical. Date values are displayed as claims, not newly reviewed applicability. Private technical/applicability findings are excluded. Text and metadata are rendered literally in the UI.

The endpoint rejects inputs larger than 200,000 characters or 2,000 lines per version before diffing. No silent truncation occurs; review narrower source units or the separate full packets. The comparison SHA-256 covers its canonical JSON `comparison` object. Identical content or a clean diff never grants authority, rights, review or Agent admission.

## General historical applicability

Migration `0012_applicability` creates the append-only application ledger `applicability_reviews`, with no inferred dates or approval backfill. Apply migrations before using the API. This workflow currently covers general/original and acquired intake passages. Bundled SEC excerpts retain their separate existing workflow; reconciling it with this durable ledger remains open.

Technical reviewers submit `POST /editorial/sources/{id}/applicability` using `ApplicabilityDecision` in OpenAPI. Fresh authentication, exact source revision/policy version and a reviewer different from the source author are required. Approval requires current independent technical review, any required parser review and full-display permission. Supply actual issuance, public availability and effective dates, explicit framework/entity scope, audit regime for audit sources, scope/findings, private supporting-record reference/hash, expiry and actual-review attestation. Open-ended effective intervals require explicit confirmation. Future issuance/public availability claims and reversed intervals are rejected. Future effective dates are possible; they do not imply present applicability.

Source locks serialize concurrent decisions; stale submissions fail. Each decision appends a private record and increments source policy version. Approval binds the technical and parser records as well as source content; new technical/parser decisions require fresh applicability review. Revocation remains possible after rights or technical approval is lost. `GET` on the same endpoint returns the latest 100 private records in policy-version order under current display/output permissions. Findings are not copied into public source policy. Hashes are integrity checks, not signatures or independently authenticated professional evidence.

Retrieval and saved evidence access/export check the reviewed public-availability date against knowledge date and the effective interval against both period endpoints. Import timestamps no longer stand in for historical public availability. Unknown or mismatched framework/entity/audit scope, expired or changed records and unresolved conditions withhold evidence. Intake passages additionally need an explicit period end. Conditions can be recorded, but all conditional records currently withhold automated evidence until a case-specific review workflow exists; free-text early-adoption claims cannot bypass this. Approved dates update effective fields while preserving intake manifest claims. Undated generic sources without an applicability record retain their existing behavior; this is not a universal approval of their applicability.

No reviewer UI for these general records is implemented yet. Jurisdiction/industry and conditional applicability resolution, SEC ledger reconciliation, actual primary-text review and human approvals remain. Test records do not advance any content coverage count.
