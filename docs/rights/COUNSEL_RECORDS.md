# Independent counsel records (#7)

This workflow records an actual authorized person's decision for a particular `reviewed_use` source revision. It does not decide fair use, verify professional credentials by itself, or create publisher permission. No real decision is included in this release. `license`, original and government-work gates remain distinct.

## Three separate actions

1. An administrator registers a metadata-only source or authorized intake manifest with explicit operation grants, restricted `license_evidence_ref`, route/audience/jurisdiction scope and applicable output terms. Existing protected-source intake restrictions still apply. Submission cannot smuggle a body into the source API.
2. An administrator submits `POST /api/v1/admin/sources/{source_id}/counsel-records`. The proposal binds the exact rights revision and current policy version, every requested operation, effective and mandatory expiry timestamps, an opaque evidence-bundle reference and SHA-256, and seven opaque assessment references: purpose, nature, amount/substantiality, output/reconstruction, market effect, access route/terms and jurisdiction. These references identify material in the operator's restricted legal-review system. `ev_` plus 8–120 alphanumeric/underscore/hyphen characters is the accepted identifier format; URLs and prose are rejected. The software does not fetch that evidence or claim its hash was independently verified.
3. A designated `counsel_reviewer` uses the restricted GET on that same path to inspect the proposal, source policy and revision, then submits `/counsel-records/{id}/review` with the exact record digest, approved/rejected decision and explicit actual-independent-review attestation. The reviewer must actually inspect the restricted evidence, exact work, proposed operations and scope. A separate `rights_approver` then uses the existing source approval API to activate it atomically with the next source policy version. The source author, proposal submitter, counsel reviewer and activating rights approver cannot collapse the prohibited pairs, even by switching roles.

The review role is persisted on the server user record. It cannot be asserted in a request, acquired through payment or granted through this API. No default or demo account receives it. The operator must identify an actual qualified authorized reviewer and provision that role through the secured administration process. Tests assign it only to synthetic fixtures. Production role provisioning/identity evidence still requires operator and security work.

The OpenAPI contract specifies the exact request fields. Routes use server-verified identity, verified email and MFA; mutations require recent authentication. Ordinary users cannot enumerate records. The restricted response contains source metadata/policy but never bypasses body-operation gates to return source text. A dedicated review UI remains under #35.

## Enforcement and revocation

An operation on a `reviewed_use` source checks an approved, unrevoked record at every existing rights checkpoint. The record digest must match its immutable proposal; work/revision, operation, activation version, review separation and effective/expiry interval must match. Both existing policy scopes and the counsel gate apply. Output limits, technical/applicability review, workspace access, subscription and source seats remain independent. Route/audience/jurisdiction are mandatory in a reviewed-use proposal's source policy; the decision does not invent runtime jurisdiction, publisher-seat or provider-retention evidence. Those scopes require separate [verified records](VERIFIED_SCOPES.md); counsel approval alone never supplies them.

Counsel approval alone enables no body operation. An old Boolean source approval, a nonempty evidence reference or a detached in-memory source also cannot bypass the decision. Reapproval requires a new current-version decision; old evidence cannot revive after an approval version bump. Future decisions cannot activate early; expiry immediately withholds dependent use through existing retrieval/model/output/export checks.

An authorized administrator, rights approver or counsel reviewer may revoke using `/counsel-records/{id}/revoke`, with expected digest and a closed reason code. Revoking the active decision increments the source policy version and removes reviewed status; duplicate revocation is idempotent. Revoking a pending/inactive request does not invalidate unrelated active work. Rejected/revoked records cannot be changed back to approved. Source-row locks serialize review, activation, disable and revocation; counsel records are reloaded at runtime even in a previously loaded worker session.

The audit stores action, actor, record/source ID, revision digest or closed reason code, not legal prose or evidence references. The database itself remains private; counsel proposal references are not public source metadata and are not included in general audit responses. The API schema cannot prevent a trusted operator from entering inappropriate data elsewhere; retention, encrypted backups, secure evidence-vault integration and counsel-record deletion policy remain production work.

Revocation does not recall a provider request already transmitted or a file already downloaded. Physical deletion of retained raw/derived data, indexes and backups remains open. Cumulative output accounting is unchanged; this workflow does not provide policy-limit amendments or authorize resetting work counters.

## Observed verification

The synthetic suite covers missing/pending decisions, separate roles and activation, exact work/revision, rejected/revoked records, expiry boundaries, altered proposals, operation/scope mismatch, missing assessments, prohibited free text, public/audit privacy, and dependent-output revocation seen by a previously loaded worker session. PostgreSQL tests exercise competing activations and activation/revocation races. Actual commands/results and infrastructure evidence are recorded in `progress.md` and `reports/counsel/`. No synthetic reviewer or passing test is a real legal review.
